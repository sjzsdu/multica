# 架构决策记录 (ADR) 与系统设计

## ADR 标准结构

每个架构决策产出一个 ADR，格式：

```
ADR-[编号]: [一句话决策]

## 状态
[提案 | 接受 | 废弃 | 替换]

## 背景
描述问题上下文、约束条件、触发因素。

## 决策
我们决定做什么。

## 理由
- 列出 2-3 个关键备选方案
- 对比维度：复杂度、可靠性、可观测性、团队熟悉度、长期维护成本
- 为什么选这个

## 后果
- 正面：...
- 负面：...
- 成本：...

## 迁移路径（如适用）
- Phase 1: ...
- Phase 2: ...
- 回滚策略：...
```

## 技术选型评估框架

每次选型必须至少对比 2 个替代方案，在以下维度打分：

| 维度 | 权重 | 评估内容 |
|---|---|---|
| 团队熟悉度 | 高 | 学习曲线、招聘难度 |
| 长期维护 | 高 | 社区活跃度、版本节奏、API 稳定性 |
| 可观测性 | 高 | 能否接入 tracing/metrics/logging |
| 可靠性 | 高 | 故障模式、恢复时间、边界情况 |
| 扩展性 | 中 | 能撑到什么量级 |
| 性能 | 中 | 是否是瓶颈，能否优化 |
| 开发效率 | 中 | 部署、调试、工具链 |
| 生态兼容性 | 低 | 与现有系统集成成本 |

## 系统设计原则

- **先跑通，再抽象**：不要为"未来需求"设计；YAGNI
- **单一职责 + 显式边界**：每个模块/服务有清晰的输入输出契约
- **失败是常态**：设计能优雅降级和恢复的路径，不要假设零失败
- **状态在哪里**：每个状态要么持久化，要么明确声明为缓存；不能模糊
- **数据一致性**：分布式场景下选 CP 还是 AP，写清楚理由
- **可演进**：所有架构决策都要有迁移路径，没有"不可回退"的选择

## Agent-Native 架构考量

- Agent 可调用层（Tool 契约）要足够清晰，让 Agent 能理解参数含义和边界
- 错误信息要足够让 Agent 自行恢复，不是必须人介入
- 状态持久化到 Agent 能 resume 的粒度（checkpoint）
- 人类审批点设计在高价值决策，不是每个小步骤
