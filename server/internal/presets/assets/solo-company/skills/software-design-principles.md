# 软件设计原则（全栈工程师核心）

## 核心信念

**代码是写给人读的，顺便让机器执行。** 可维护性 > 巧妙 > 性能（除非性能已证实是瓶颈）。

## 一、SOLID 原则（落地版，不是教科书）

### S — 单一职责

一个模块/类/函数只因为**一个理由**而改变。

**判断方法**：如果一个函数同时处理"数据获取"和"数据格式化"，把它们拆开。你能给它起一个不带"And"的名字吗？不能就该拆。

**反例**：`handleUserRequest` 里既解析参数、又查数据库、又格式化响应、又记日志。

### O — 开闭原则

对扩展开放，对修改关闭。**新功能通过加代码实现，不改已有代码。**

**实现手段**：
- 用接口/抽象类型，不依赖具体实现
- 用策略模式、工厂模式，不用 if-else 链
- 用组合，不用继承

**反例**：加一种新的 assignee 类型，就要改 `getAssignee` 里的 switch。应该让每种 assignee 实现同一个接口。

### L — 里氏替换

子类必须能在不破坏正确性的前提下替换父类。

**实战**：如果你写了一个子类，调用方需要"先判断是不是这个子类再调用"，就违反了 LSP。

### I — 接口隔离

不要强迫客户端依赖它不用的方法。**接口要小而专一。**

**反例**：一个 `UserRepository` 接口有 20 个方法，但某个调用方只用 `findById`。拆成 `UserReader` / `UserWriter`。

### D — 依赖倒置

高层模块不依赖低层模块，两者都依赖抽象。**依赖指向抽象，不指向具体。**

**实战（最重要）**：
- 业务逻辑不直接 import 数据库实现，依赖 `Repository` 接口
- 不直接 `import axios`，依赖 `HttpClient` 接口
- 不直接读 `process.env`，依赖 `Config` 接口
- 好处：可测试、可替换、可独立演进

**判断**：看 import 列表。如果业务代码 import 了具体的数据库/HTTP/文件系统实现，多半违反了 DIP。

## 二、DRY — 不要重复自己

**重复是万恶之源**：改一个 bug 要改 N 处，总有一处漏掉。

### 什么时候该抽象

| 重复次数 | 动作 |
|---|---|
| 1 次 | 直接写 |
| 2 次 | 可以忍，但标记 |
| 3 次 | **必须抽象** |

### 抽象的正确姿势

- 抽**相同的逻辑**，不是相似的代码。两段代码长得像但意图不同，不该合并
- 用"参数化"代替"复制"：把变化的部分变成参数
- 共享的逻辑放共享层，不共享的逻辑各自实现

### 反模式

- **过早抽象**：为"以后可能复用"建抽象，结果没人用。YAGNI。
- **错误抽象**：把不同意图的代码硬合并，用参数 + flag 区分。这比重复更糟。

## 三、设计模式（什么时候用，不要炫技）

**设计模式是解决常见问题的标准答案，不是目标。** 不需要每个项目都用满 23 种。

### 高频实用模式

| 模式 | 适用场景 | 不要在...时用 |
|---|---|---|
| **策略模式** | 同一行为有多种算法，运行时切换 | 只有一种实现 |
| **工厂模式** | 对象创建逻辑复杂，或需要根据条件创建不同类型 | `new` 一行就能搞定 |
| **观察者模式** | 一对多的事件通知 | 一对一直接调用就行 |
| **适配器模式** | 已有接口不符合新需求，又不能改 | 直接改接口更简单 |
| **装饰器模式** | 动态给对象加行为，且组合灵活 | 继承一层就够 |
| **代理模式** | 控制访问（缓存、权限、延迟加载） | 没有额外控制需求 |
| **状态模式** | 对象行为随状态变化，有大量 if-else | 状态少于 3 个 |

### 反模式（比不用更糟）

- **为用而用**：代码里硬塞策略模式，其实只有一个策略
- **过度设计**：一个简单需求套 3 层抽象
- **上帝类**：一个类 2000 行，啥都干——该拆

## 四、依赖注入（DI）

依赖从外部传入，不在内部创建。

### 好处
- 可测试：测试时传 mock
- 可替换：换实现不用改业务代码
- 显式依赖：函数签名说清楚需要什么

### 实战
```ts
// 坏：在函数里 new
class UserService {
  private repo = new UserRepository(); // 硬依赖
}

// 好：从外部注入
class UserService {
  constructor(private repo: UserRepository) {} // 依赖接口
}
```

### 不滥用
- 简单脚本不需要 DI 框架
- 依赖只有一个实现且不会变，直接用也行
- 关键是**业务逻辑和副作用解耦**，不是非要用 DI 容器

## 五、解耦的判断标准

两个模块耦合了，当且仅当：**改 A 必须改 B 才能不出错。**

### 降低耦合的手段

1. **依赖接口，不依赖实现**（DIP）
2. **数据结构稳定，实现可换**
3. **单向依赖**：A → B → C，不要 A → B 且 B → A（循环依赖）
4. **事件驱动**：用事件/消息代替直接调用
5. **最小暴露**：只暴露需要暴露的，其他设为 private/internal

### 耦合的红线

- 循环依赖（必须解）
- 业务逻辑依赖框架实现（必须解）
- 共享可变状态（必须避免或加锁）

## 六、命名即设计

好的命名是最好的文档。

| 坏名字 | 好名字 | 问题 |
|---|---|---|
| `data` | `userProfile` | 没说是什么 |
| `process` | `validateAndSave` | 没说做什么 |
| `flag` | `isEmailVerified` | 没说真假代表什么 |
| `handleUser` | `createUserSession` | 太模糊 |
| `temp` / `tmp` | （根据用途命名） | 临时变量也要有意义 |

## 七、代码评审时检查清单

- [ ] 这个函数/类有单一职责吗？
- [ ] 高层逻辑依赖抽象了吗？（DIP）
- [ ] 有没有重复 3 次以上的代码？（DRY）
- [ ] 加新功能需要改已有代码吗？（OCP）
- [ ] 有没有循环依赖？
- [ ] 命名能让陌生人看懂吗？
- [ ] 有没有为"以后"设计但现在用不上的抽象？（YAGNI）

## 原则的优先级冲突时

**可维护性 > 简洁 > 性能 > 巧妙。**

当 DRY 和可读性冲突，选可读性（重复比难懂好）。
当 OCP 和简单性冲突，选简单（除非已证实需要扩展）。
当性能和可维护性冲突，先写可维护的，证实慢了再优化。
