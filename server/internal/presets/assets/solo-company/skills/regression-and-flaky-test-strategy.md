# 回归与 Flaky 测试治理

## 一、回归范围怎么定

**全量回归是奢侈品，目的是在不漏关键风险的前提下砍掉无用功。**

### 影响面分析（先做这个）

从改动出发反向推导受影响的测试：

1. `git diff` 看改了哪些文件/包
2. 沿**依赖方向**向下找消费方（谁 import 了这个模块）
3. 沿**数据流**找共享状态（DB 表、缓存 key、API 契约、事件）
4. 标出跨边界改动（schema、协议、公共组件、配置）——这些必须扩大回归范围

### 分级回归

| 触发条件 | 回归范围 |
|---|---|
| 改单个函数内部实现 | 该模块单元测试 |
| 改公共模块 / shared package | 所有消费方的单元 + 集成 |
| 改 API 契约 / DB schema | 全量集成 + 关键 E2E |
| 改鉴权 / 支付 / 数据迁移 | 全量回归 + 人工验收 |
| 依赖大版本升级 | 全量回归 + 性能基线对比 |

### 必测清单（不受影响面分析影响）

只改一行也要跑：鉴权、权限边界、核心写入路径、数据迁移、并发相关。

## 二、基线维护

**没有基线的回归等于没回归**——你不知道"通过"是恢复到原状，还是一直就那样。

- **功能基线**：关键路径的预期输出快照。更新基线必须人工确认 diff，禁止无脑 `-u` 覆盖
- **性能基线**：记录 P50/P95/P99 和吞吐量，波动阈值明确（如 P95 劣化 > 20% 即失败）
- **覆盖率基线**：不低于上次，下降要在 PR 里解释
- **基线本身也要评审**：基线错了一次，后面所有回归都是错的

## 三、Flaky 测试治理

**Flaky 测试是最有害的技术债**：它训练团队忽略红色，最终真 bug 也被当噪声。

### 归因分类

| 类型 | 特征 | 处置 |
|---|---|---|
| **测试自身的时序问题** | 缺 await、固定 sleep、异步未同步 | 改等待条件为轮询断言，不用 `sleep` |
| **共享状态污染** | 单跑通过、全量失败 | 每例独立 fixture，测试间无共享可变状态 |
| **外部依赖不稳** | 网络、第三方 API、时钟 | 打桩或注入可控时钟 |
| **并发竞争** | 概率性失败，日志显示交错 | 要么真实暴露产品 bug，要么加锁/隔离 |
| **资源耗尽** | 连接池、端口、文件句柄 | 补清理逻辑（finally / teardown） |
| **数据残留** | 上次运行的数据影响下次 | 用唯一标识生成测试数据 |
| **环境差异** | 本地过 CI 挂 | 固定时区/语言/随机种子，环境变量显式化 |

### 处置流程

1. **记录**：失败的运行 ID、日志、出现频率（如 3/100）
2. **复现**：单跑 N 次、`-count=10`、并行跑，确认是 flaky 还是稳定失败
3. **定性**：是测试问题还是产品 bug？
   - **测试问题** → 修测试
   - **产品 bug**（并发、状态泄漏、时序假设）→ **按 bug 处理，不是按测试处理**
4. **隔离**：无法立即修就标记 `quarantine` / `skip` 并**建 issue + 设期限**，不能默默留着
5. **回归**：修好后连跑 20 次确认

### 禁止做法

- 加重试直到通过（掩盖问题，且真实 bug 也在重试里消失）
- 调大超时（慢失败只是变成更慢的失败）
- 直接删除不稳定测试（等于放弃该覆盖点）
- 把 flaky 当"正常现象"

## 四、CI 门禁分层

| 层 | 触发 | 内容 | 时长目标 |
|---|---|---|---|
| 快速门禁 | 每次 push | lint + typecheck + 单元测试 | < 5 min |
| 合并门禁 | PR | 集成测试 + 关键 E2E + 覆盖率阈值 | < 20 min |
| 完整回归 | 合并到主干 / 发版前 | 全量 E2E + 性能基线 + 迁移验证 | 异步可接受 |

**门禁必须是阻断性的**。只告警不阻断的门禁相当于没有门禁。

## 五、回归报告怎么写

```
## 回归范围
改动文件 → 影响模块 → 覆盖的测试集（说明为什么这个范围够）

## 结果
- 通过：N
- 失败：N（逐条给根因归属：产品 bug / 测试问题 / 环境）
- 跳过：N（逐条给原因和期限）

## 基线变化
功能快照 diff、性能指标对比、覆盖率变化

## Flaky 状态
本轮新发现的 flaky 及其归因和处置
```

## 六、常见误区

- **把"测试通过"当"功能正确"**：回归只证明没退化，不证明新功能对
- **回归范围全凭感觉**：要做影响面分析，不能"上次跑这些这次也跑这些"
- **基线长期不更新**：基线漂移后回归变成噪声
- **只测 happy path**：回归最容易漏的是错误路径的退化
