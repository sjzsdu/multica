# 全项目审计方法论

## 与逐次复核的区别

| | 逐次复核（门禁） | 全项目审计 |
|---|---|---|
| 触发 | 每次改动 | 里程碑 / 发版前 / 定期 |
| 输入 | 有明确验收标准 | 自己建立判定标准 |
| 策略 | 深度优先，逐条验收 | 广度优先，风险排序后分层深入 |
| 输出 | PASS / FAIL verdict | 分级问题清单 + 基线 |
| 目标 | 挡住这次的问题 | 看清整体风险分布 |

**审计不是把每个文件都读一遍。** 是先用低成本手段画出风险地图，再把预算投到最贵的地方。

## 三层推进

### 第一层：全景扫描（低成本，覆盖 100%）

目标是**发现哪里值得深挖**，不是发现问题本身。

- 目录结构与模块边界：包大小、文件数、依赖方向
- 规模与变化热度：最近改动的文件（`git log --name-only` 统计）、最大的文件、最常改的文件
- 依赖清单：直接依赖数量、锁文件是否一致、明显过期或冗余的包
- 构建与检查：lint / typecheck / build / test 是否能跑通，实际耗时
- 配置与入口：环境变量清单、启动路径、密钥来源
- 已有测试分布：哪些模块有测试、哪些完全没有

产出：一张**风险地图**——标注"高改动 + 低测试 + 跨边界"的区域。

### 第二层：按风险排序，选审计目标

排序因子（相乘，不是相加）：

1. **影响面**：出问题时会伤到什么（数据、钱、权限、核心流程）
2. **改动热度**：最近是否频繁改动
3. **测试强度**：有无测试、测试是否有效
4. **复杂度**：并发、状态机、跨模块、外部依赖
5. **不可逆性**：出错后能否回滚

### 第三层：分层深入（预算集中在这里）

- **P0 区域**：逐条路径走读 + 构造复现验证，不接受"看起来没问题"
- **P1 区域**：走读关键路径 + 抽样验证失败分支
- **P2 区域**：只看结构性问题（重复、耦合、缺测试）
- **P3 区域**：只记录，不深入

## 抽样原则

无法穷举时，抽样必须可解释：

- **关键路径 100% 覆盖**：鉴权、权限、数据写入、迁移、支付、并发路径不能抽样
- **边缘模块按风险抽样**：每个模块至少抽 1 条主路径 + 1 条失败路径
- **边界优先于中间**：抽空值、极值、超长、非法状态，比抽正常值发现的问题更多
- **新代码优先**：最近改动的地方缺陷密度最高
- **同一模式抽到第 3 次就停**：如果 3 处都犯了同样的错，记录下来定性为系统性问题，不再逐处验证

## 证据分级（强制）

每条发现必须标注等级，不允许混淆：

| 等级 | 含义 | 要求 |
|---|---|---|
| **已复现** | 实际触发并观察到后果 | 给命令 / 步骤 + 观察到的结果 |
| **路径推演** | 代码路径明确会出错，但未实际跑 | 给出具体调用链和触发条件 |
| **待确认** | 有可疑信号，需进一步验证 | 说明怀疑点和验证方法 |

**禁止**：把"待确认"写成结论，把"代码风格不好"写成缺陷。

## 七类检查维度

1. **正确性与数据一致性**：核心业务路径、状态机、事务边界、并发、幂等、部分失败
2. **安全与权限**：认证、授权、越权、输入处理、密钥、日志泄漏（见 security-audit-checklist）
3. **架构与可维护性**：依赖方向、循环依赖、分层腐化、重复、过度抽象、上帝模块
4. **测试有效性**：关键路径是否被覆盖、断言是否有效、失败路径是否有测试、flaky、测试与实现是否耦合过紧
5. **性能与资源**：慢查询、N+1、无界分页、无界缓存、连接与句柄泄漏、长任务阻塞
6. **可运维性**：日志是否可诊断、错误是否可区分、指标是否覆盖业务结果、配置是否可解释
7. **依赖与供应链**：已知漏洞、版本漂移、锁文件一致、废弃包、安装脚本风险

## 风险分级

| 级别 | 定义 | 处置 |
|---|---|---|
| **P0 阻塞** | 数据丢失/损坏、鉴权绕过、越权、敏感信息泄漏、不可恢复的不一致 | 修复前不应继续发版 |
| **P1 严重** | 特定条件下必然出错、核心路径缺测试、无界资源增长 | 本迭代修 |
| **P2 中等** | 边缘场景缺陷、明显的技术债、可诊断性差 | 排期修 |
| **P3 建议** | 风格、命名、可读性、优化空间 | 顺手修或忽略 |

**只报 P2/P3 的审计报告没有价值**——必须明确回答"有没有 P0/P1"。

## 审计报告结构

```
## 结论摘要
- P0: N 项 | P1: N 项 | P2: N 项 | P3: N 项
- 是否可以继续发版（是 / 修完 P0 后 / 否）
- 最需要关注的三件事

## 风险地图
哪些区域高危、为什么（影响面 × 热度 × 测试强度）

## 问题清单（按级别排序）
每条：
- ID / 级别 / 维度
- 位置（文件 + 行号 / 模块）
- 现象
- 证据（等级 + 复现方式或调用链）
- 影响（什么场景下会怎样）
- 建议（改什么，不改也行要说明代价）
- 是否系统性问题（同类还有几处）

## 已建立的基线
- 构建/测试/lint 的实际状态与耗时
- 关键性能基线
- 测试覆盖的实际情况（哪些模块零覆盖）

## 未覆盖范围
- 本次没审到的部分及原因
- 建议下一轮优先审计什么

## 待建 issue 列表
- 可直接复制为 issue 的条目（标题 + 级别 + 验收标准）
```

## 审计反模式

- **陷入单点深挖**：在第一层就花 2 小时看一个文件，全景没画出来
- **无证据断言**："这里可能有并发问题"——要么给调用链，要么标"待确认"并给验证方法
- **泛泛建议**："建议加强测试""建议优化架构"——不可执行，等于没说
- **改代码**：审计者动手就失去独立视角，且污染被测基线
- **只看新代码**：老模块的系统性问题往往更严重
- **把覆盖率当结论**：低覆盖率是信号，不是缺陷本身
- **报喜不报忧**：为了显得项目健康而降低分级，是最坏的失职

## 基线的作用

审计产出的一半价值是**基线**。下一轮审计时用同一套指标对比，才能看出是变好还是变坏。没有基线，第二轮审计只能重新主观判断。
