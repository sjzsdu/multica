# 测试设计技术

目标是**用最少的用例抓住最多的缺陷**，不是把清单打完勾。先问"哪些输入空间等价"，再决定测几个。

## 一、等价类划分

把输入空间切成若干类，每类内部行为一致，**每类取一个代表值即可**。

- **有效等价类**：合法输入。每个类至少 1 个用例
- **无效等价类**：非法输入。每个类**单独** 1 个用例（不要和有效输入混在一起，否则不知道是哪条规则拦下来的）

示例：字段 `age`，要求 18–65 的整数
| 类 | 取值 | 类型 |
|---|---|---|
| 太低 | 17 | 无效 |
| 合法下界 | 18 | 有效 |
| 合法中值 | 40 | 有效 |
| 合法上界 | 65 | 有效 |
| 太高 | 66 | 无效 |
| 非整数 | 40.5 | 无效 |
| 非数字 | "abc" | 无效 |
| 空 | null / "" | 无效 |

## 二、边界值分析

缺陷高度集中在边界。等价类只是起点，**边界必须单独测**。

取每个边界的：**边界值本身、边界内侧、边界外侧**

```
有效区间 [18, 65]
必测：17, 18, 19, 64, 65, 66
```

常见边界：0、-1、1、空集合、单元素、最大长度、最大长度+1、off-by-one、时间边界（23:59:59、月初月末、闰年 2/29、时区切换）

## 三、判定表（多条件组合）

当输出由**多个条件的组合**决定时，用判定表穷举规则，避免漏掉组合。

| 条件 | R1 | R2 | R3 | R4 |
|---|---|---|---|---|
| 已登录 | Y | Y | N | N |
| 有权限 | Y | N | Y | N |
| → 结果 | 允许 | 403 | 401 | 401 |

每个规则至少 1 个用例。**注意条件之间的隐含依赖**（未登录时"有权限"无意义 → 用 `-` 表示不关心）。

## 四、Pairwise / 正交实验

条件数 > 4 时全组合爆炸（5 个 3 值参数 = 243 种）。**大多数缺陷由 1–2 个参数的交互触发**，pairwise 能把组合压到 O(n²) 且保留这个覆盖度。

做法：列出所有参数和取值 → 生成两两组合覆盖的用例集 → 补充业务关键的三元组合。

适用：配置矩阵、兼容性矩阵（浏览器 × OS × 分辨率）、feature flag 组合。

## 五、状态迁移测试

有明确状态机的对象（订单、任务、审批、Agent 运行状态），**测的是迁移，不是单个状态**。

1. 画出状态图（状态 + 合法迁移）
2. 覆盖：每条合法迁移至少 1 次
3. **重点覆盖非法迁移**：从每个状态尝试所有不合法的目标状态，必须被拒绝
4. 覆盖不可达状态（从初始态无法到达的状态是设计缺陷）

示例检查：`running → completed` 合法，`completed → running` 必须拒绝。这类逆向迁移是漏测重灾区。

## 六、场景法 / 用户旅程

按真实用户路径串起来测，覆盖跨模块交互和状态持久化。适合 E2E 层。

选路径的原则：主流程 1 条 + 每个分支出口 1 条 + 每个异常恢复路径 1 条。

## 七、错误猜测

基于经验和历史缺陷，列出"最容易错的地方"定向验证：
- 最近改动过的代码（`git log` 看变化）
- 历史上出过 bug 的模块
- 并发、时序、缓存、重试
- 空值、超长、特殊字符、Unicode、emoji
- 时区、夏令时、本地化

## 八、按风险分配测试预算

不是所有功能都值得同样多的用例。用 **风险 = 影响 × 概率** 排序：

| 风险 | 测试投入 |
|---|---|
| 高影响 + 高概率 | 全技术栈覆盖（单元 + 集成 + E2E + 故障注入） |
| 高影响 + 低概率 | 重点做故障注入和边界 |
| 低影响 + 高概率 | 单元 + 1 条集成 |
| 低影响 + 低概率 | 冒烟即可，甚至不测 |

## 用例写作要求

每条用例必须能独立判定通过/失败：

```
用例 ID：TC-xxx
前置条件：具体状态（数据、登录态、配置）
步骤：可复现的操作序列
输入：具体值
预期：可观察的具体结果（状态码、字段值、UI 状态）
```

**禁止**："测试登录功能正常"——不可判定。
**正确**："用已注册邮箱 + 正确密码登录 → 返回 200，响应含 token，跳转 /dashboard"。

## 覆盖率怎么用

| 指标 | 能说明 | 不能说明 |
|---|---|---|
| 行覆盖 | 哪些代码被执行 | 分支逻辑对不对 |
| 分支覆盖 | 每个 if 的两个方向都走到 | 组合条件是否完整 |
| 路径覆盖 | 更多组合 | 数据边界 |

**覆盖率是"没测到的地方"的探测器，不是质量指标。** 100% 覆盖也可能全是无效断言。反过来，关键模块覆盖率低就是明确风险，要写进验收报告。

## Agent / 异步系统的额外设计点

- **时序**：任务被中断后恢复、重复投递、乱序到达
- **幂等**：同一请求发两次，结果是否一致
- **部分失败**：多步操作中途失败，已完成的步骤是否被正确回滚或标记
- **超时**：每个外部调用的超时路径，以及超时后的重试是否风暴
- **凭证失效**：token 过期/被吊销时的行为（报错还是静默失败），错误码是否可区分
