# 调试手册

## 核心流程：复现 → 假设 → 验证 → 修复 → 确认

**不要一上来就改代码。** 90% 的调试时间应该花在定位根因，不是在试错。

## 第一步：复现

- 写出最小复现步骤
- 确认是必现还是偶现
- 偶现问题：记录出现频率、触发条件、环境差异
- 无法复现 → 加日志，等下次出现

## 第二步：收集证据

| 证据来源 | 看什么 |
|---|---|
| 错误日志 | 完整 stack trace、错误消息、请求 ID |
| 应用日志 | 出错前后的操作序列、关键变量值 |
| 数据库 | 相关行的状态、时间线 |
| 网络 | 请求/响应 payload、状态码、耗时 |
| 浏览器 DevTools | Console、Network、React 组件树 |
| Git | 最近改了什么（`git log --oneline -20`） |

**铁律：日志里不能打 token / secret / 个人敏感信息。**

## 第三步：形成假设

- 根据证据列出 2-3 个可能的根因
- 每个假设必须可证伪
- 按可能性排序，先验证最可能的

### 常见根因类别

1. **状态错误**：变量值不符合预期（竞态、初始化、缓存）
2. **边界条件**：空值、超长、负数、零除
3. **类型错误**：string vs number、null vs undefined
4. **时序问题**：异步没 await、事件顺序、回调时机
5. **依赖问题**：第三方 API 变更、版本不兼容、网络
6. **配置问题**：环境变量、feature flag、权限

## 第四步：验证假设

- **二分法**：注释掉一半代码，看问题是否消失
- **隔离法**：在独立环境复现，排除其他干扰
- **对比法**：找一个能正常工作的类似 case，对比差异
- **加日志**：在关键节点打印中间值，确认哪一步开始出错
- **不要**：同时改多个地方，否则不知道哪个修好了

## 第五步：最小修复

- 只改根因，不改周边
- 不要顺手"优化"不相关代码
- 修复要能解释"为什么之前错、现在对"

## 第六步：确认

- 原问题复现步骤现在通过
- 没有引入回归（跑相关测试）
- 如果是并发/竞态问题，跑多次确认
- 如果是边界条件，加测试覆盖

## 调试反模式

| 反模式 | 后果 |
|---|---|
| 没复现就改代码 | 改了不知道对不对 |
| 一次改多处 | 不知道哪个生效、引入新 bug |
| 靠"感觉"猜 | 浪费时间在错的方向 |
| 改完不跑测试 | 引入回归 |
| 删日志不保留证据 | 下次同样问题又从零开始 |
| `console.log` 到处撒 | 污染输出，忘了删 |

## 性能调试专属

- **先测后改**：用 profiler（Go pprof / React Profiler / Chrome DevTools Performance）确认瓶颈，不要靠猜
- 看 P95/P99，不看平均值（平均值掩盖长尾）
- 数据库慢：开慢查询日志 + EXPLAIN
- 前端慢：看 React render 次数、bundle 大小、网络瀑布

## Agent 调试专属

- token 失效：看 401 错误码是 `invalid_token` 还是 `task_token_revoked`，区分"不存在"和"被吊销"
- 任务中途 401：检查 jcode session 复用是否冻结了旧 token
- checkpoint 恢复失败：检查 task_id + dispatched_at 是否匹配
- 用 `--debug` 抓原始响应体，不要只看中文错误提示
