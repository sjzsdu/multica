# 界面质量验证

## 界面缺陷分五类，工具各管一段

| 类型 | 表现 | 手段 | 能否进门禁 |
|---|---|---|---|
| 功能性 | 点不动、跳错页、提交失败 | E2E 断言 | 是 |
| 视觉性 | 布局塌陷、文字溢出、错位 | 截图基线对比 | 是 |
| 状态缺失 | 空态空白、错误态未处理、无权限崩溃 | 六状态矩阵截图 | 部分 |
| 规范性 | 字体混乱、层级过重、AI 味 | 代码级规则审查 | 是（静态） |
| 体验性 | 流程绕、文案怪、切状态丢信息 | agent 实际走查 | 否，只能探索 |

不要指望一个工具解决全部。**门禁要确定性，走查要覆盖率。**

## 一、六状态矩阵（交付前必做）

每个核心界面固定覆盖六态：

1. 默认（有数据、正常态）
2. 空数据
3. 加载中
4. 错误（请求失败 / 校验失败）
5. 无权限
6. 超长文本 + 窄屏

AI 生成界面最常见的缺失是 2、4、5。**功能写完立刻补这三态，比事后补便宜得多。**

只在 3–5 个高频界面做，不要全站铺开。

## 二、视觉回归（进门禁）

- 用测试框架自带的截图断言（如 Playwright `toHaveScreenshot`），不为这件事引第三方服务
- **基线必须在与 CI 相同的 OS + 浏览器版本生成**。本地 macOS 生成的基线在 Linux CI 上几乎必然失败
- **动态内容必须 mask**：时间戳、头像、实时图表、随机 ID
- **设容差**（如 maxDiffPixels）。追求 0 像素差异是不现实的目标，会导致这套机制被弃用
- 基线文件纳入版本管理；更新基线必须人工确认 diff，禁止无脑覆盖
- 截图前等界面稳定：网络空闲 + 字体加载完成 + 动画结束

## 三、规范审查（静态，读代码即可）

不需要启动浏览器。检查：是否使用了通用默认字体、层级是否过重（每个按钮都是主按钮）、卡片是否嵌套、间距是否走 token、颜色是否散落硬编码、是否滥用渐变文字或玻璃效果。

这一层和视觉回归不重复：视觉回归回答"有没有变坏"，规范审查回答"本来就对不对"。

## 四、探索式走查

适合用 agent 驱动的浏览器（如 ego-lite）做，发现"功能都对但用起来荒谬"的问题。

适合它的场景：
- 复杂登录态，自建测试账号成本高
- 界面改版频繁，选择器维护成本高
- 需要自主走完整流程而不是验证单个断言

边界（必须遵守）：
- 结果具有概率性，同一流程可能给出不同结论
- 依赖外部工具与平台环境，**不得放进阻断式门禁**
- 输出的是观察而非断言，须由人判定严重程度

用法：UI 改动后走一遍关键路径，产出体验问题清单，分级后转待办。

## 交付物

UI 改动必须附带：

- 六状态截图，缺哪态要说明原因
- 视觉 diff 结果（若已建基线）
- 已知缺口：哪些状态没做、为什么不做

## 反模式

- 追求 0 像素差异，导致视觉回归被整体关掉
- 用重试压掉不稳定的截图失败，而不是修根因
- 把视觉回归当功能测试（它只证明"长得一样"，不证明"用得了"）
- 全站铺截图基线，维护成本压垮团队
- 只截默认态，空态和错误态从不验证
- 用文字描述代替截图（"我看了没问题"不构成证据）
