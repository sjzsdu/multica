# 一人公司架构硬约束

## 三条铁律

1. **没有"未来扩展性"这个需求**。能跑、能卖、能退出才是需求。
2. **每个技术选择都要回答"我关门时怎么办"**。答不出就不能上。
3. **你一个人就是最大的单点故障**。架构要假设你某天不想维护它。

## 一、成本上限（默认 $0-50/月）

超过就必须论证"为什么这个钱花得值"。

### $0-50/月 预算下的推荐组合

| 用途 | 推荐 | 成本 |
|---|---|---|
| 前端 | Vercel / Cloudflare Pages | $0 |
| 后端 | Vercel Functions / Cloudflare Workers / Fly.io 免费档 | $0 |
| 数据库 | Supabase 免费 / Neon 免费 / Turso 免费 | $0 |
| 认证 | Supabase Auth 免费 / Auth.js 自托管 | $0 |
| 支付 | LemonSqueezy（按交易抽成） | $0 固定 |
| 邮件 | Resend / Plunk 免费档 | $0 |
| 监控 | Uptime Kuma 自托管 | $0 |
| 分析 | PostHog 免费额度 | $0 |
| **合计** | | **$0** |

### 触发"必须升级"的信号

- 数据库：免费额度被打满、需要 PITR 备份
- 托管：冷启动影响转化、免费档休眠
- 邮件：免费额度不够发

**不要因为"感觉要爆"就升级，要看到真实数据再升。**

## 二、运维复杂度上限

一个产品同时在线的"会动的东西"上限：

| 类别 | 上限 | 理由 |
|---|---|---|
| 独立部署的服务 | ≤ 3 | 超过就要维护多个 CI/CD、监控、日志 |
| 数据库实例 | ≤ 1 | 两个以上要维护同步/备份策略 |
| 定时任务 | ≤ 5 | 超过就分不清哪个挂了 |
| 第三方 SaaS 依赖 | ≤ 8 | 每个都要管账单、API key、限额 |
| 消息队列 | 0-1 | 能不用就不用 |

**超过上限的做法**：合并服务、换更集成的 SaaS、砍功能。不是"再加一个"。

## 三、退出策略检查

每个技术选型必须过这一关：

| 检查项 | 合格 | 不合格 |
|---|---|---|
| 数据能否导出 | 一键导出标准格式 | 私有格式/无导出 |
| 代码能否迁移 | 标准框架，换托管即可 | 深度绑定某 SaaS 私有 API |
| 关停成本 | 删号即走 | 需要数据迁移、用户通知、合同解约 |
| 转让成本 | 接手人能看懂 | 依赖你的私有脚本和记忆 |

**一票否决**：如果某个 SaaS 让你在它的私有 API 上写了超过 500 行业务代码，要重新评估。

## 四、时间预算

单人周开发时长有限（通常 20-40h），技术选择对时间的影响：

### 省时间（优先）
- 用 SaaS 替代自建（Auth、支付、邮件、监控）
- 用托管数据库替代自托管
- 用成熟框架而非自研
- 用现成 UI 库（shadcn/ui、Tailwind）而非从零设计

### 费时间（警惕）
- 自建 CI/CD（用 GitHub Actions 现成的）
- 自建监控（用 SaaS）
- 上 Kubernetes（一人公司几乎永远不需要）
- 上微服务（单体 + 模块化就够）
- 学新语言/新框架（除非现有栈真的做不了）

## 五、MVP 阶段反模式清单

**MVP 阶段绝对不要上的东西**：

| 反模式 | 替代方案 |
|---|---|
| Kubernetes | Vercel / Fly.io / Railway |
| 微服务架构 | 模块化单体 |
| Redis 缓存 | 数据库查询先优化，真的慢了再说 |
| 消息队列（RabbitMQ/Kafka） | pg-boss / cron + DB 表 |
| Elasticsearch | PostgreSQL 全文搜索 |
| 自建推荐系统 | 简单规则 / SQL 排序 |
| GraphQL | REST（除非真的需要） |
| 自研 ORM / 框架 | 成熟方案 |
| 多区域部署 | 单区域 + CDN |
| 实时协作（CRDT） | 轮询 / 简单 WebSocket |
| 复杂的权限系统 | 简单的 owner/member 两档 |
| Docker Swarm | docker-compose / PaaS |

**判断标准**：如果某个技术让你在 MVP 阶段多花超过 2 天，而它的价值要等 1000 用户才体现，就不要上。

## 六、什么时候可以"过度设计"

只有一种情况：**你已经验证过这个东西能卖出去，且当前的简单方案正在成为瓶颈**。

信号：
- 数据库慢查询日志出现真实的慢查询
- 单服务响应时间 P95 > 1s
- 用户明确抱怨性能
- 免费额度真的被打满

**没有这些信号，"扩展性"就是伪需求。**

## 输出要求

做架构决策时，必须显式回答：

1. 月成本增加多少？（含隐性成本如运维时间）
2. 会动的东西增加了几个？
3. 我关门/转让时这个东西怎么办？
4. 现在不做这个，会失去什么？（答不出就是不需要）
